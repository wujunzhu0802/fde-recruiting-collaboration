# 运营节奏、事件与复盘

## 30 / 60 / 90天计划

30天：协调员每日看未确认积压，质量每周抽查误报漏报，系统工程师核对规则版本与错误日志。关键错误0容忍，未确认超过2工作日提示升级。阈值是建议值，需业务确认。

60天：叶书与顾明岚核对逐单处理/返工/等待、采用率和人工复核新增成本，重新计算ROI。若只改变回填时间但没有减少实际处理，不计收益。

90天：复审授权用途、规则版本和资产使用，决定持续、扩展或退役。真实收益不达标则维持人工模板或终止接入。当前没有模型，不设置虚构的模型漂移指标；监测字段缺失率、版本不一致率、格式变化和规则误报。

## INC-DEMO-01：旧证书偏好传播

触发依据fsg-recruiting-f11。本地测试向version=2的岗位输入brief_version=1反馈，规则检测STALE_VERSION；质量不能带阻断项确认。处置路径：停止问题交接→登记原问题与来源→识别受影响单→业务核对证书偏好→修正当前资料→新建核对单→复核确认。

根因假设：旧表仍将取消的偏好当作硬要求，变更未随单据传递。需以原始版本验证，不能把假设写成真实根因。修复后回归分类、旧版反馈、来源缺失、权限、幂等、排期与退回路径。本地恢复记录保存于verification.json，客户与质量事件问答保存于virtual-reviews.json。真实发生/恢复时刻、影响人数和生产损失没有测量，保持未提供。

## 变更控制

每次变更记录提出人、原始资料版本、修改理由、审批人、测试哈希、发布时间和回退点。重新执行全部回归，仍需检查旧版反馈被阻断。严禁直接修改已确认单而掩盖旧结论；用新请求记录保存变化。
